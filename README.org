/bridge Woodpecker CI to Byggsteg pipelines/

Integrate [[https://codeberg.org/jjba23/byggsteg][Byggsteg]] pipelines easily into your [[https://woodpecker-ci.org/][Woodpecker CI]] setup (for example at Codeberg), with three tiny Alpine-based pipeline steps.

------------------

* What this is

Woodpecker runs a pipeline as a series of container steps. Byggsteg runs CI/CD
jobs described as Lisp (Scheme) thunks. This repository is the bridge between
the two: three small pipeline steps that let a Woodpecker pipeline authenticate
to Byggsteg, hand it a job, and faithfully report the job's outcome back to
Woodpecker -- so a Woodpecker build goes green or red according to what Byggsteg
actually did.

The steps are plain Bash on top of Alpine Linux. They pull in only ~bash~,
~curl~ and ~ca-certificates~ (everything else they use is already in busybox),
each image lands around 16 MB, and they stay deliberately small so CI pulls and
job startup stay fast.

** The three steps

|------------------------------------+---------------------------------------------------------|
| *Image*                            | *Role*                                                   |
|------------------------------------+---------------------------------------------------------|
| ~byggsteg-woodpecker-get-token~    | Authenticate to Byggsteg and store the session token.    |
| ~byggsteg-woodpecker-submit-job~   | Submit a Lisp job definition, get back its log id.       |
| ~byggsteg-woodpecker-poll-job~     | Poll until the job finishes; pass or fail the build.     |
|------------------------------------+---------------------------------------------------------|

------------------

* How it works

The three steps run in order and talk to each other through files in Woodpecker's
shared workspace (the working directory every step runs in):

#+begin_example
            get-token                 submit-job                poll-job
   ┌───────────────────┐    ┌────────────────────────┐   ┌────────────────────┐
   │ POST /api/v1/login│    │ POST /api/v1/jobs/...   │   │ GET /api/v1/logs/… │
   │  ──> token        │    │  ──> log-id             │   │  … until done      │
   └─────────┬─────────┘    └───────────┬────────────┘   └─────────┬──────────┘
             │                          │                          │
     x-bewaking-byggsteg ──────> byggsteg-log-id ────────> (status + output)
#+end_example

The files exchanged between steps are:

|-------------------------------+-----------------------------------------------------------|
| *File*                        | *Written by / read by*                                    |
|-------------------------------+-----------------------------------------------------------|
| ~x-bewaking-byggsteg~         | written by get-token, read by submit-job                  |
| ~byggsteg-log-id~             | written by submit-job, read by poll-job                   |
| ~byggsteg-submit-job-response.json~ | written by submit-job (the submit response body)    |
| ~byggsteg-log-response.json~  | written by poll-job (the last status response body)       |
|-------------------------------+-----------------------------------------------------------|

** What you see in the logs

The steps are deliberately quiet. Each prints a line or two as it works, and:

- *on success or failure, poll-job prints the job's output* (the log Byggsteg
  recorded for it) exactly once -- nothing is dumped while the job is still
  running;
- *on success, submit-job prints the JSON Byggsteg answered with* (the ~log-id~
  and title);
- every error goes to stderr, in red, prefixed with a timestamp.

So a green build shows you the job's output and little else, and a red build
shows you the same output plus the reason it failed -- no per-poll noise.

* Example usage

#+begin_src yaml
variables:
  - &submit_job_image 'docker.io/jjba23/byggsteg-woodpecker-submit-job:v0.1.34'
  - &poll_job_image 'docker.io/jjba23/byggsteg-woodpecker-poll-job:v0.1.34'
  - &get_token_image 'docker.io/jjba23/byggsteg-woodpecker-get-token:v0.1.34'
  - &jointhefreeworld_byggsteg_url 'https://byggsteg.jointhefreeworld.org'
  - &main_branch 'trunk'

clone:
  - name: "⬇️ Clone Git repository"
    image: woodpeckerci/plugin-git
    settings:
      depth: 1

steps:
  get-byggsteg-token:
    name: "🔒 Get token @ Byggsteg"
    image: *get_token_image
    when:
      - event: [ push ]
        branch: [ *main_branch ]
    settings:
      BYGGSTEG_URL:
        from_secret: BYGGSTEG_URL
      BYGGSTEG_EMAIL:
        from_secret: BYGGSTEG_EMAIL
      BYGGSTEG_PASSWORD:
        from_secret: BYGGSTEG_PASSWORD

  submit-byggsteg-job:
    name: "💼 Submit job @ Byggsteg"
    image: *submit_job_image
    when:
      - event: [ push ]
        branch: [ *main_branch ]
    settings:
      BYGGSTEG_URL: *jointhefreeworld_byggsteg_url
      BYGGSTEG_JOB_CODE: |
        (lambda()
          `((task . ("make-test" "pull-and-deploy"))
            (project . "%%CI_REPO_NAME%%")
            (branch-name . "%%CI_COMMIT_BRANCH%%")
            (clone-url . "%%CI_REPO_CLONE_URL%%")))

  poll-byggsteg-job:
    name: "🔄 Poll job status @ Byggsteg"
    image: *poll_job_image
    when:
      - event: [ push ]
        branch: [ *main_branch ]
    settings:
      BYGGSTEG_URL: *jointhefreeworld_byggsteg_url
#+end_src

Woodpecker turns each ~settings~ key into a ~PLUGIN_*~ environment variable that
the step reads (so ~BYGGSTEG_URL~ is seen by the script as
~PLUGIN_BYGGSTEG_URL~). The step scripts also have access to the whole Woodpecker
build context, which is what makes the ~%%CI_*%%~ placeholders in
~BYGGSTEG_JOB_CODE~ work: before submitting, submit-job replaces every
~%%NAME%%~ with the value of the environment variable ~NAME~.

------------------

* Settings reference

Settings are the Woodpecker ~settings~ keys; each becomes a ~PLUGIN_~-prefixed
environment variable for the step.

** byggsteg-woodpecker-get-token

|----------------------------+-----------+------------------------------------------------|
| *Setting*                  | *Default* | *Meaning*                                      |
|----------------------------+-----------+------------------------------------------------|
| ~BYGGSTEG_URL~             | --        | Base URL of your Byggsteg instance.            |
| ~BYGGSTEG_EMAIL~           | --        | Email of the Byggsteg account.                 |
| ~BYGGSTEG_PASSWORD~        | --        | Password/key of that account.                  |
|----------------------------+-----------+------------------------------------------------|

It ~POST~s to ~/api/v1/login~ and stores the ~x-bewaking-byggsteg~ token the
response carries in the file ~x-bewaking-byggsteg~ for later steps.

** byggsteg-woodpecker-submit-job

|--------------------------+-----------+--------------------------------------------------|
| *Setting*                | *Default* | *Meaning*                                        |
|--------------------------+-----------+--------------------------------------------------|
| ~BYGGSTEG_URL~           | --        | Base URL of your Byggsteg instance.              |
| ~BYGGSTEG_JOB_CODE~      | --        | The Lisp job definition (see the example above). |
|--------------------------+-----------+--------------------------------------------------|

It reads the token file, expands the ~%%...%%~ placeholders in the job code,
~POST~s to ~/api/v1/jobs/manage/submit~ and stores the returned ~log-id~ in the
file ~byggsteg-log-id~.

** byggsteg-woodpecker-poll-job

|---------------------------------+-----------+--------------------------------------------|
| *Setting*                       | *Default* | *Meaning*                                  |
|---------------------------------+-----------+--------------------------------------------|
| ~BYGGSTEG_URL~                  | --        | Base URL of your Byggsteg instance.        |
| ~POLL_LIMIT~                    | ~4096~    | Maximum number of status polls before the  |
|                                 |           | step gives up and fails the build.         |
| ~POLL_INTERVAL_SECONDS~         | ~8~       | Seconds to wait between polls.             |
|---------------------------------+-----------+--------------------------------------------|

It reads the log id, then ~GET~s ~/api/v1/logs/<log-id>~ until Byggsteg reports
~success~ or ~failure~. ~success~ exits 0, ~failure~ exits 1, and reaching the
poll limit exits 1 as a timeout.

** Advanced: retry tuning

The token and submit steps retry transient failures (network problems, HTTP
errors). Fine-tune the retries with plain environment variables if the defaults
are too impatient or too eager:

|--------------------------------+-----------+----------------------------------------|
| *Variable*                     | *Default* | *Meaning*                              |
|--------------------------------+-----------+----------------------------------------|
| ~BYGGSTEG_RETRY_ATTEMPTS~      | ~8~       | Total attempts before the step fails.  |
| ~BYGGSTEG_RETRY_INTERVAL~      | ~4~       | Seconds to wait before the next retry. |
|--------------------------------+-----------+----------------------------------------|

* Developing

The project's tasks are declared in ~maak.scm~ and run with
[[https://codeberg.org/jjba23/maak][Maak]]; ~maak --list~ shows them all:

#+begin_src sh
maak build              # build the three step images
maak push               # build (if needed) and push the three step images
maak build get-token    # ...or a single step
maak lint               # shellcheck the step scripts and the test runner
maak fmt                # format them with shfmt
maak test               # run the end-to-end tests
maak sizes              # report the size of each built image
maak clean              # remove the locally built images
#+end_src

The images are built with ~podman~ and published to DockerHub. The image tag is
the exact git tag you are standing on (or the short commit hash, away from a
tag); set ~VERSION~ to name it yourself. Override the registry or organisation
for your own builds with ~IMAGE_REGISTRY~ and ~IMAGE_ORG~:

#+begin_src sh
IMAGE_REGISTRY=ghcr.io IMAGE_ORG=yourname maak build push
#+end_src

** Linting and testing

~maak lint~ runs [[https://www.shellcheck.net/][shellcheck]] over the step scripts and the test runner, and
~maak fmt~ formats them with [[https://github.com/mvdan/sh][shfmt]].

~maak test~ runs the end-to-end suite in ~test/~. It starts a small mock of the
Byggsteg API ([[file:test/mock-byggsteg.scm][test/mock-byggsteg.scm]], written in Guile -- the language Maak
already needs) and points the step scripts at it, so the whole suite needs
nothing but ~bash~, ~curl~ and ~guile~: no image build and no Byggsteg instance.
It covers the happy paths and the ways they go wrong, including the errors worth
having a mock for:

|--------------------------+--------------------------------------------------------|
| *Scenario*               | *What it checks*                                         |
|--------------------------+--------------------------------------------------------|
| ~success~                | token stored, job submitted, job passes                   |
| ~failure~                | a job that fails fails the step (exit 1)                  |
| ~timeout~                | a job that never finishes times out, with no poll noise   |
| ~login-error~            | a login answering 500 exhausts the retries                |
| ~submit-error~           | a submit answering 500 exhausts the retries               |
| ~login-no-token~         | a login answering 200 with no token fails                 |
| ~submit-not-json~        | a submit answering with a non-JSON body fails             |
| ~submit-no-log-id~       | a submit answer without a log-id fails                    |
| ~status-not-json~        | an unrecognizable status fails at once, not at the limit  |
|--------------------------+--------------------------------------------------------|

The last four are answers that are wrong without being errors: a 200 that
carries no token, a body that is not the JSON the step expects, JSON without
the field it needs.  The steps must fail on those rather than pass on nothing --
and the tests pin that down, checking the exit code and that an unrecognizable
status fails on the first poll instead of running out the clock.

It also checks the errors that are the operator's to fix: a step run out of
order (submit without a token, poll without a log id) and a step missing its
required settings.

** How big the images are

Each of the three images is Alpine with one short list of packages and the two
scripts it runs:

- *packages:* ~bash curl ca-certificates~ -- three, down from eight (~jq~,
  ~coreutils~, ~make~, ~grep~ and ~ncurses~ used to be installed too);
- *size:* about ~16.5 MB~ per image on disk, down from about ~30.7 MB~;
- *files:* the shared ~prelude.bash~ and the step's own script.

Everything else the scripts reach for is already in busybox (~date~, ~sed~,
~tr~, ~head~, ~base64~, ~sleep~). There is deliberately no ~jq~: the Byggsteg
responses are small, flat JSON objects, so the few fields the steps read are
pulled out with bash pattern matching, and neither ~jq~ nor the ~oniguruma~ it
drags along has to be downloaded at the start of every pipeline step. ~maak
sizes~ prints the measured size of each image you have built.

* Troubleshooting

- *"missing token file: x-bewaking-byggsteg"* -- the submit step ran without the
  get-token step before it (or in a different workspace). Keep the three steps
  in the same pipeline, in order.
- *"missing log-id file: byggsteg-log-id"* -- the poll step ran without a
  successful submit step before it.
- *Login fails with a 401* -- check ~BYGGSTEG_EMAIL~ / ~BYGGSTEG_PASSWORD~.
  The get-token step retries and then fails; the HTTP error is printed.
- *"Timed out waiting for Byggsteg job"* -- the job ran longer than
  ~POLL_LIMIT × POLL_INTERVAL_SECONDS~. Raise ~POLL_LIMIT~ or the interval.
- *Job output looks truncated* -- what is printed is exactly what Byggsteg
  recorded (~log-data~); the raw status response is also kept in the workspace,
  in ~byggsteg-log-response.json~.
